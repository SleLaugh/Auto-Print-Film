# 第七阶段 GDCM 写盘串行保护设计

## 问题与证据

第七阶段会先串行完成一组 MPR 采样，再由多个窗位线程分别进行灰度映射和
DICOM 输出。现场在四个窗位同时写第一张 DICOM 时触发
`double free or corruption (fasttop)`：四个窗位目录均留下同一时刻创建的
零字节 `.gdcm.*.tmp.dcm`，且没有进入后续 pydicom 标签校正。这说明故障位于
同一进程内多个 `SimpleITK.ImageFileWriter` 并发调用 GDCM 的原生写盘阶段。

该故障是线程时序相关的原生竞态，单次成功不能证明并发写盘安全。髋骨解剖
坐标、第六阶段计划和 MPR 采样均已在故障发生前完成，与本问题无关。

## 设计

保留不同窗位的线程池以及 NumPy 灰度映射并行，只对 GDCM 写盘临界区加进程内
全局互斥锁。锁的范围包含 `ImageFileWriter` 的创建、配置、`Execute` 和销毁，
确保任何时刻最多只有一个 GDCM 写入器存活。CT 成片和定位图使用同一个
写盘入口和同一把锁，避免两个调用路径重新形成并发。

正式切片完成后，各窗 Localizer 不再留在窗位线程中并行准备。第七阶段先在
主线程冻结同一计划的 `ImagePositionPatient` 和 `ImageOrientationPatient`，再按
窗位串行执行灰度映射、DICOM 写出和 debug PNG 写出。这样除了避免 GDCM 原生
并发，还保证四个窗只改变灰度和序列标识，不会因 SimpleITK 元数据复制时序偶发
退回二维默认方向。任一必要空间标签缺失时，定位图写出必须在正式文件发布前失败。

pydicom 的层厚、层间距校正仍在 GDCM 成功写出后执行；不同窗位使用独立目录、
临时文件和序列 UID，现有原子替换逻辑不变。不通过降低线程数掩盖问题，也不
引入多进程和额外中间影像。

## 验证

增加确定性并发测试，以四个线程同时调用真实 `write_ct_dicom` 流程，并用可观测
写入器替代原生 GDCM。修复前的无锁基线会出现多个写入器重叠；当前带锁实现的
最大活动写入器数必须为 1，同时四个输出均成功生成。

另增加多窗 Localizer 测试：正式切片窗位任务仍在线程池中执行，但四个定位图
调用必须全部发生在主线程，收到完全相同的冻结位置和方向；真实写盘后四个 DICOM
的两项空间标签必须逐值一致。缺少空间标签的定位图不得生成正式文件。

随后执行第七阶段聚焦测试、全量测试、Python 编译及 `git diff --check`。优先使用
现有髋骨 `raw_0000.nii.gz` 和 `slice_plans.json` 单独执行第七阶段；若运行目录已被
新任务清空，则在相同 `fuseblk` 文件系统上用 41 张、512 级矩阵的四窗位计划执行
等规模原生写盘压力验证。检查每个窗位的成片数量、定位图可读性和隐藏临时
文件残留，全程不重新运行 nnUNet。
