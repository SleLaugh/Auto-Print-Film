交付报告和 Python 响应见 [响应契约设计](2026-10-08-交付报告与响应契约设计.md)。

> **当前适用边界：** 本文与
> [`2026-08-11-八阶段流水线职责拆分设计.md`](2026-08-11-八阶段流水线职责拆分设计.md)
> 共同生效；阶段名称、顺序和职责以八阶段设计为准。

## 1. 目标

在不改变已有医学算法的前提下，把当前可运行的脚本收口成可配置、可验证、
可追踪、可安全扩展的处理框架。

本轮只建设五个基础模块：

1. 统一配置与启动前检查；
2. 阶段输入输出契约；
3. 任务和阶段生命周期；
4. 任务目录与产物管理；
5. 标准化错误体系。

## 2. 非目标

本轮不做以下工作：

- 不实现或调整回正算法；
- 不增加新的部位、切割方式、重建状位或模型；
- 不改变现有层厚、层间距、窗宽窗位和 DICOM 生成规则；
- 不引入数据库、消息队列、Web API、桌面界面或并发任务调度；
- 不在 Pipeline 层实现断点续跑、通用阶段重试和任务取消，只为这些能力保留稳定接口；
  第二阶段对外部 nnUNet 进程提供可配置时限及最多一次恢复重试，见
  [配置校验设计](2026-10-08-配置校验与回归门禁设计.md)，不重跑后续阶段；
- 不迁移到 Pydantic 等新框架，继续使用标准库 `dataclasses`，避免扩大依赖面。

## 3. 总体架构

当前 Pipeline 固定编排八个职责阶段。框架组件围绕 Pipeline 工作，不侵入各阶段的
医学计算：

```text
CLI / Python caller
        |
        v
ConfigLoader ---- CapabilityRegistry
        |                  |
        +------> PreflightValidator
                         |
                         v
                    JobContext
                         |
                         v
Request -> Pipeline -> StageContract[] -> Response
              |              |
              |              +--> typed StageResult
              |
              +--> ArtifactManager
              +--> ErrorInfo / WarningInfo
              +--> manifest.json
```

调用入口负责解析请求；配置加载器负责形成唯一的生效配置；预检器在业务目录清理
或外部推理之前验证环境，但失败报告和日志仍可能写出；Pipeline 负责编排生命周期；阶段负责业务处理，
但通过有类型的结果对象交接；产物管理器统一分配和清理路径；任务清单记录全过程。

## 4. 模块边界

### 4.1 配置模块

新增 `src/config/settings.py`，定义：

- `AppConfig`：应用总配置；
- `NnUNetConfig`：nnUNet 路径和执行选项；
- `LoggingConfig`：分别管理调试产物、控制台和三类文件日志开关；
- `PipelineConfig`：失败策略和产物保留策略。

`src/config/loader.py` 负责读取合并、严格解析布尔值，并校验统一部位配置；病例几何仍由各阶段校验。

nnUNet 配置优先级为（日志及 Pipeline 段采用显式值覆盖默认值）：

```text
显式调用参数 > 对应环境变量 > 默认配置文件 > 内建默认值
```

2026-10-13 发布方式更新：`nnuNet_config.json` 当前保留本机模型目录和外部推理入口，
首次构建沿用，迁移时按目标机器调整。空的 nnUNet 模型路径表示沿用环境变量，
不能被转换成当前工作目录。发布程序的 JSON 外置于程序目录的 `src/config/`，
不依赖调用方工作目录。

配置加载形成冻结字段的 `AppConfig`，但其嵌套字典不是深度不可变对象。
调用方应视其为只读；部分阶段仍有独立配置加载入口，不应承诺所有执行路径只读一次 JSON。
阶段构造函数接收从 `AppConfig` 转换出的配置字典，不自行形成第二套应用配置。

### 4.2 能力注册与预检

新增 `src/core/capabilities.py`，集中声明当前实际支持的：

- 检查类型；
- 部位；
- 切割方式；
- 重建状位；
- 模型规则。

能力注册表是请求校验和 planner 选择的共同事实来源，CLI 的枚举仍可表达未来能力，
但未注册的组合必须在 Pipeline 启动前返回明确错误，不能运行到切片规划阶段才失败，也不能
静默跳过请求状位。

新增 `src/core/preflight.py`，按以下顺序执行只读检查：

1. 请求结构合法；
2. 请求组合在能力注册表中受支持；
3. 输入目录存在且可读取；
4. 输出目录的父目录可用；
5. 配置的外部 nnUNet 命令或外部 Python 可访问；未配置命令时才从 PATH 查找
   `nnUNetv2_predict`，不要求应用环境安装 nnUNet/PyTorch；
6. 唯一模型根目录 `nnUNet_results` 已配置且存在，不检查训练数据目录，具体模型能否推理仍在第二阶段验证；
7. 输入输出不相等且不能互相包含，缓存目录不能等于或位于输出目录内。

预检器本身只读，失败时不清理旧业务结果、不推理；但入口/Pipeline 的失败兜底会尽力
创建或更新 `report.json`，日志也可能已经写入。不能承诺整个失败调用绝不写输出目录。

### 4.3 阶段契约

`src/models/stage_results.py` 为当前八个阶段提供顶层结果类型：

- `PreprocessingResult`；
- `SegmentationResult`；
- `SpatialCorrectionStageResult`；
- `LocalizationStageResult`；
- `AnatomicalAnalysisStageResult`；
- `PlanningStageResult`；
- `ReconstructionStageResult`；
- `ReportingStageResult`。

结果模型第一轮只约束阶段间真正使用的稳定字段。调试详情仍可放入
`diagnostics: Dict[str, Any]`，避免一次性重写所有内部结构。

每个结果共同包含：

- `schema_version`；
- `stage_name`；
- `warnings`；
- `artifacts`；
- `diagnostics`。

新增 `StageArtifact`，字段包括 `artifact_type`、`path`、`retention` 和可选的
`description`。路径统一使用字符串序列化，在内存中由产物管理器转换为 `Path`。

`ProcessingContext` 通过 `set_stage_result()` 登记有类型结果，通过 `set_result()`、
`get_result()` 提供序列化后的业务字典。需要强类型校验的调用使用
`require_stage_result()`；类型不匹配或缺少前置结果时抛出框架错误，而不是在阶段内部
出现 `KeyError`。

### 4.4 任务和阶段生命周期

新增以下枚举：

```text
JobStatus: pending, running, succeeded, failed, cancelled
StageStatus: pending, running, succeeded, failed, skipped, cancelled
```

`ProcessingContext` 新增：

- `job_id`：Context 构造时生成 UUID，当前构造参数没有外部 ID 注入入口；
- `job_status`；
- `stage_records`；
- `started_at`、`finished_at`；
- `effective_config_summary`；
- `software_version`。

每个 `StageRecord` 记录状态、开始/结束时间、耗时、错误、警告和结果 schema 版本。
Pipeline 是唯一允许改变任务和阶段状态的组件；Stage 只返回结果或抛出异常。

状态转换规则固定为：

```text
job:   pending -> running -> succeeded | failed | cancelled
stage: pending -> running -> succeeded | failed
stage: pending -> skipped | cancelled
```

本轮继续采用 `fail_fast`：任一必需阶段失败后停止，后续阶段标记 `skipped`。
配置中预留失败策略字段，但本轮不开放其他行为。

cancelled 枚举是预留能力；KeyboardInterrupt/SystemExit 等 BaseException 走最外层失败
报告兜底并重新抛出，不保证 Context 或 manifest 已完整转换为 cancelled。

### 4.5 任务目录与产物管理

新增 `src/core/artifacts.py`，由 `ArtifactManager` 唯一负责路径创建和清理。

每次任务继续使用项目现有输出目录结构。调试模式在根目录增加 `manifest.json`，
非调试模式不生成；三类程序日志及批处理单病例日志统一写入根目录下的 `log/`，业务
阶段按需创建现有的 `metadata/`、`nifti/`、`segmentation/` 和各状位目录。

稳定接口要求：调用方传入的 `output_dir` 代表本次任务目录，不额外自动增加一层
随机目录；`job_id` 写入 manifest。批处理系统以后应为每个任务传入独立目录。

产物保留级别：

```text
final         始终保留
intermediate  成功时按配置清理，失败时默认保留
debug         只在 debug_file_enabled=true 时生成并保留
log           按日志配置保留
```

`output_dir` 定义为本次任务专用目录。所有只读预检通过后，Pipeline 清理已有业务结果
并重新创建任务目录，避免旧结果混入本次任务；任务启动后已经打开的 `log/` 目录是唯一
保留项。日志正文和分类规则不变，每个任务直接写入固定的 `RunLog.txt`、
`DebugLog.txt`、`ErrorLog.txt` 和 `BatchLog.txt`，不再增加日期或小时子目录。

`ArtifactManager` 只负责任务开始前重建输出根目录、登记已有阶段产物以及写 manifest，
不改变横状位、矢状位、冠状位等现有业务输出位置。

### 4.6 标准化错误体系

新增 `src/core/errors.py`：

```text
FrameworkError
├── ConfigurationError
├── RequestValidationError
├── CapabilityError
├── DependencyError
├── StageInputError
├── ExternalProcessError
├── ArtifactError
└── OutputValidationError
```

每个错误包含：

- `code`：稳定机器码；
- `message`：用户可读中文消息；
- `stage`：可选阶段名；
- `retryable`：是否适合上层重试；
- `details`：不含患者敏感信息的诊断字段；
- 原始异常可通过异常链保留；失败交付报告仍包含可读错误消息。

未知异常统一包装成 `UNEXPECTED_ERROR`，详细堆栈只进入错误日志或 debug 报告。
manifest 阶段错误保留 code/retryable/details，Response.errors 仅返回 stage/message，两者格式不同。

## 5. Manifest 设计

仅当 `debug_file_enabled=true` 时，任务开始后立即原子写入 `manifest.json`，
并在阶段状态变化后更新。先写临时文件，再使用同目录替换，避免进程中断留下半个
JSON。非调试模式不创建 manifest。

最低结构：

```json
{
  "schema_version": "job_manifest_v1",
  "job_id": "uuid",
  "status": "running",
  "created_at": "ISO-8601",
  "started_at": "ISO-8601",
  "finished_at": null,
  "software_version": "1.0.0",
  "request": {},
  "effective_config": {},
  "stages": [],
  "artifacts": [],
  "warnings": [],
  "errors": []
}
```

`effective_config` 只保存可复现所需的非敏感摘要，不保存患者信息、环境变量全集或
本机秘密。当前摘要记录 nnUNet 参数和路径是否配置，不记录完整模型路径；模型 ID 在分割结果中。
manifest 的 request、产物路径和错误文字仍可能包含本机路径，当前没有自动脱敏层，外发前须审查。

## 6. 数据流与失败行为

正常流程：

1. CLI 解析 `Request` 和显式配置；
2. `ConfigLoader` 形成 `AppConfig`；
3. `PreflightValidator` 完成全部只读检查；
4. `ArtifactManager` 安全初始化任务目录；
5. Pipeline 创建 manifest，把任务设为 `running`；
6. 每个阶段由 Pipeline 更新状态并执行；
7. Stage 返回有类型结果，Context 校验并登记产物；
8. 每个状态边界原子更新 manifest；
9. 全部阶段完成后清理允许删除的中间产物；
10. 任务标记 `succeeded` 并返回 Response。

失败流程：

1. 预检失败：不清理旧业务结果、不新建 manifest；尽力写失败报告后重新抛出错误；
2. 目录初始化失败：不启动任何阶段；
3. 阶段失败：阶段标记 `failed`，后续阶段标记 `skipped`；
4. 中间产物默认保留用于排查；
5. manifest 标记 `failed` 并记录标准错误；
6. 清理过程失败只追加 warning，不覆盖原始业务错误。

## 7. 稳定接口策略

框架对外保持以下稳定接口：

- `Pipeline()` 仍可无参数构造；
- `Request` 的现有字段和 CLI 参数保持不变；
- `Response.to_dict()` 保留现有计数字段，同时新增 job 和状态信息；
- Context 同时提供有类型结果和序列化业务字典，两者由 `set_stage_result()` 同步生成；
- 现有业务输出路径暂不移动；
- 全量自动测试必须继续通过；
- 新框架测试不得依赖真实 nnUNet 模型或患者数据。

废弃的阶段名和结果键不保留双写或回退分支。

## 8. 测试策略

### 8.1 单元测试

- 配置来源合并优先级；
- 空路径不覆盖环境变量；
- 能力组合允许和拒绝；
- 错误序列化；
- 状态转换合法性；
- 产物路径和保留策略；
- manifest 原子写入内容；
- 有类型阶段结果的存取和类型错误。

### 8.2 Pipeline 契约测试

使用假 Stage 验证：

- 八阶段均成功；
- 中间阶段失败后后续阶段为 `skipped`；
- warning 不导致任务失败；
- 失败时保留中间产物；
- 已指定的任务输出目录会清理旧业务文件，仅保留真实 log 子目录，不依赖历史 manifest 标记；
- manifest 状态与 Response 一致。

### 8.3 回归测试

继续使用：

```bash
python -m pytest -q
```

当前 CI 已采用 pytest，并执行 compileall 与 Ruff；详见配置校验与回归门禁设计。

## 9. 安全与隐私约束

- 不主动把患者姓名等 DICOM 字段写入日志或 manifest，但异常文字和路径没有自动脱敏保证；
- 不记录完整环境变量；
- output_dir 是调用方授权清理的专用目录；ArtifactManager.prepare 不校验历史 manifest，严禁指向共享资料目录；
- 预检期间不修改输入目录；
- 输入路径和输出路径必须经过规范化后再比较；
- 调试产物默认关闭，生产配置不得默认保留分割或中间 NIfTI。
- `debug_file_enabled` 控制 manifest、调试影像和调试元数据，并使成功任务保留中间现场；
  中间文件也可由 Pipeline 的 keep_intermediate 配置保留，外部缓存独立保留；
  `debug_log_file_enabled` 只控制 `DebugLog.txt`，两个开关不得互相代替。

## 10. 实施分组

框架建设拆成五个可独立验收的任务组：

1. 配置模型、加载器和预检；
2. 错误模型、任务状态和阶段记录；
3. 产物管理器和安全输出目录；
4. 有类型阶段结果和 Context 序列化视图；
5. Pipeline 集成、manifest、回归测试和文档。

每一组都先增加失败测试，再做最小实现；不在同一任务中修改具体医学算法。

## 11. 完成标准

满足以下条件才算框架基础收口完成：

- 主流程通过统一入口组装生效配置，嵌套数据按只读约定使用；
- 不支持的请求在业务清理和推理前拒绝，仍允许写日志与失败报告；
- 调用方遵守 output_dir 专用目录语义，输入输出及缓存关系经预检；
- 每个任务和阶段都有明确状态与时间记录；
- 阶段间稳定数据通过有类型结果交接；
- Response、manifest 和日志可通过同一个 job_id 关联；
- 已知错误具有稳定错误码；
- 现有全量测试和新增框架测试全部通过；
- README 给出安装、配置、预检、运行和测试的唯一推荐命令；
- 没有新增对真实患者数据或真实模型的自动测试依赖。
