# 八阶段流水线职责拆分设计

## 1. 背景

拆分前的六阶段主链中，`LocalizationStage` 同时承担横状位 XY 校正、标签定位、
解剖坐标系和脊柱专用几何计算。这些职责的失败边界、输出契约和下游消费者
不同，继续放在一个阶段会使单独重跑、状态记录和问题定位越来越困难。

本轮只拆分阶段职责和交接契约，不修改校正角度、标签范围、四棱柱、CPR、
切片数量、DICOM 写出等医学与重建算法。

## 2. 目标主链

```text
1 Preprocessing
2 Segmentation
3 SpatialCorrection
4 Localization
5 AnatomicalAnalysis
6 Planning
7 Reconstruction
8 Reporting
```

### 2.1 空间校正

读取原始 CT 和分割，根据本次目标标签估计 XY 校正候选，并唯一决定后续使用的
`raw_for_reconstruction_path` 和 `seg_for_reconstruction_path`。输出校正参数、候选路径和
范围诊断，不计算最终解剖几何。

### 2.2 标签定位

只在校正阶段选定的分割空间中解析 label，输出质心、bbox、顺序、目标范围和
图像空间信息。校正阶段选定的稳定路径和诊断字段作为统一空间契约在定位结果中
透传给后续阶段。

### 2.3 解剖分析

当前颅脑、肺部、脊柱和髋骨生成统一解剖坐标系；脊柱额外生成过滤主体、
四棱柱、端面和标注质心等 `spine_geometry`。未适配部位返回空几何结果，不伪造
默认坐标系。

姿态质量与显示方向采用[统一姿态设计](../modules/reconstruction/2026-10-16-统一解剖姿态与三状位回正设计.md)：
`patient_reference_axes` 只规范存储轴的患者方向符号，SI 朝 LPS `+Z`，不改物理
坐标换算或已有斜角。镜像需通过 LR 方向唯一性检查；肺部还需验证候选面两侧的
主体分离和跨主体反射对应。S1 按实际 `label_targets` 优先解析为 `vertebrae_S1`、
否则回退 `sacrum`，整体轴诊断与椎间配对使用实际名，标准范围配置保持不变。

### 2.4 切片规划

原 `MappingStage` 的业务语义实际是切片规划，现统一更名为 `PlanningStage`。它合并
定位与解剖分析结果，生成完整 `SlicePlan[]`，决定范围、方向、层数、层厚、层间距、
基础 FOV 和 CPR 路径，并透传 fill_percent。

### 2.5 图像重建与结果校验

第七阶段保持原切面与沿法向层位置，由整组目标决定共同取景倍率，正数 FillPercent
对所有部位逐张按当前厚层内目标居中（空层回退组中心），0/null/省略维持原有组中心与基础间距。
取景后的每张 DICOM 记录真实位置，面内原点可逐层变化，不能直接假定为规则直角三维体。
第七阶段把每个计划的几何类型、层厚、层间距、切片数、窗位数和输出
目录写入重建摘要。第八阶段读取磁盘最终 DICOM，硬校验数量、编号、UID、空间标签、
层厚层间距、Localizer 和同计划跨窗几何。只有全部通过后才能在 `report.json` 中发布
`Success=true` 的正常结果；失败时抛出 `OUTPUT_VALIDATION_ERROR`，写入
`Success=false` 和错误 `Message`，debug 模式保留完整校验清单，但不得把失败结果包装成
成功交付报告。

`report.json` 同时作为任务终态文件。Python 入口和 Pipeline 最外层负责覆盖所有可捕获
异常及主动中断；对 `kill -9`、原生库崩溃、OOM 强制终止等无法在子进程内执行写盘的
情况，外部执行服务必须在进程退出后校验报告是否存在且可解析，不满足时原子补写
`Success=false` 的兜底报告。若输出目录本身不可写，则只能由执行服务记录数据库失败
状态，不能承诺生成磁盘文件。

## 3. 实施边界

- 已验证的医学几何 helper 由三个阶段共用，阶段入口和结果契约彼此独立。
- `MappingStage`、`MappingStageResult` 和 `mapping` 结果键一次性删除，仓库内调用全部改用
  `PlanningStage`、`PlanningStageResult` 和 `planning`。
- `ReconstructionStage` 从 `planning` 读取切片计划，不保留旧 `mapping` 别名；
  同时读取定位阶段确定的原图、分割路径和目标标签以执行整组取景，不能依赖运行时 label 快照。
- 调试文件名、最终 DICOM 目录、`SlicePlan` 协议和现有医学字段保持不变。

## 4. 运行时快照

后续新增的持久缓存属于第一、二阶段文件复用，不是本节快照；见
[缓存设计](2026-10-08-预处理与分割缓存设计.md)。第七阶段的取景职责见
[FillPercent 设计](../modules/reconstruction/2026-10-08-整组居中与FillPercent取景设计.md)。

三个新阶段会在同一 `ProcessingContext` 中复用一份不序列化的 label 快照，避免每个阶段
重复扫描全体素分割。快照只是性能优化；任一阶段在快照不存在时，都必须能根据前置
阶段的稳定路径和序列化字段重建所需数据。

快照的生命周期严格限定为第三至第五阶段。第五阶段是最后一个消费者，必须在
`finally` 中从 `ProcessingContext.metadata` 删除快照，使完整分割数组、逐标签体素索引、
目标 mask 和 SimpleITK 图像在阶段返回后可被正常回收。第六至八阶段只能使用正式阶段
结果，不得为方便继续引用运行时快照，也不主动调用会造成全进程停顿的 `gc.collect()`。

## 5. 日志与诊断输出

- Pipeline 框架通过 `RunLog` 统一输出阶段序号、八阶段稳定名称、中文职责、开始/完成
  状态和阶段耗时；业务输入、几何诊断和性能明细继续使用 `DebugLog`。
- 阶段失败时记录序号、稳定标识、中文职责、异常类型、错误原因和调用堆栈，并逐项记录
  因 fail-fast 跳过的后续阶段。
- 各业务阶段保留中文编号日志头，第一至第八阶段与默认主链顺序一致。
- `manifest.json` 的 `stages`、`Response.stages` 和调试报告 `timings` 使用稳定英文阶段名，
  不保留 `mapping` 结果键。
- 自动测试必须 mock Pipeline 的日志入口；测试用的 `one/two` 阶段和 `boom` 异常不得
  写入真实 `RunLog`、`DebugLog` 或 `ErrorLog` 文件。
- `ErrorLog` 在 RunLog 开启时同步写入运行日志，确保只开启 RunLog 的生产配置仍能
  留下完整失败上下文。
- `debug_file_enabled` 控制 manifest、调试影像、调试元数据及中间现场保留；
  `debug_log_file_enabled` 只控制 `DebugLog.txt`，开启调试日志不能隐式生成调试文件。
- metadata 中的调试 NIfTI 只由第五阶段写出；`DebugLog` 按文件记录输出路径和生成
  耗时，标签、椎体主体和四棱柱掩膜必须分别计时。第三阶段和第六阶段不生成调试
  NIfTI。
- `RunLog`、`DebugLog`、`ErrorLog` 及批处理单病例日志统一写入本次任务输出目录下的
  `log/`，与 `report.json` 同级；分别固定为 `RunLog.txt`、`DebugLog.txt`、
  `ErrorLog.txt` 和 `BatchLog.txt`，不再按日期、小时或病例名增加目录和文件名，日志正文
  和分类规则保持不变。
- `localization_result.json`、`slice_plans.json` 等调试产物文件名保持不变，避免影响现有
  人工检查流程；文件内规划数据由 `planning` 阶段生成和消费。

## 6. 验收条件

1. 默认 Pipeline 有且仅有八个阶段，顺序与本文一致。
2. 三个新阶段分别登记有类型结果和独立生命周期状态。
3. 校正后的 raw/seg 空间在定位、解剖分析、规划和重建中保持一致。
4. 现有四棱柱、区间切线、CPR 和重建回归测试继续通过。
5. 调试开启时的既有产物路径保持不变，最终报告只使用新的阶段结果键。
6. 日志、manifest、Response 和调试报告中的阶段顺序与八阶段主链一致。
7. 第八阶段发现 DICOM 数量、UID 或几何错误时，任务失败且不生成交付报告。
