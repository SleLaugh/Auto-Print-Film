# 相同影像序列的缓存复用

此功能默认关闭。服务端继续按原参数调用 Python，仅额外传入同一检查下各序列的母目录。
Python 负责查找和校验缓存，不需要服务端判断标签、模型或缓存是否准备完成。

## 开启与调用

在外置 `src/config/nnuNet_config.json` 中保留原字段，并合并以下配置：

```json
{
  "pipeline": {
    "series_reuse_enabled": true
  }
}
```

也可设置环境变量 `AUTOPRINTFILM_SERIES_REUSE_ENABLED=true`；环境变量优先于文件，
Python 调用时显式传入的 `pipeline.series_reuse_enabled` 优先于环境变量。

命令行在原命令后增加：

```bash
--series-cache-parent /home/peng/04_data/Project/FTPFiles/Temp/AISliceCache/0001/10000166
```

`--series_cache_parent` 是兼容写法。现有 `--cache_dir` 继续指向本序列自己的 `cache` 目录。
仓库内 `服务端/AISliceDicomService.cs` 已在启动 Python 时，根据既有
`<检查>/<序列>/cache` 路径推导检查母目录并补传此参数，不参与影像匹配、标签判断或队列变更。
请求字典使用 `series_cache_parent`，同时接受兼容字段 `SeriesCacheParent`：

```json
{
  "dicom_dir": "/input/current-series",
  "output_dir": "/check/10000166/71703/肺部",
  "cache_dir": "/check/10000166/71703/cache",
  "series_cache_parent": "/check/10000166",
  "ScanThickness": 1.5,
  "SlicePart": "肺部",
  "StudyType": "CT"
}
```

配置关闭或未传母目录时走原处理流程。开启后，目录不可用、未找到匹配项、缓存缺失或损坏
均回退原流程。旧缓存没有新版本的完整索引与处理快照时，也按未命中处理。
启用时还会校验原始 DICOM 与本序列 NIfTI 的来源记录；历史 NIfTI 缺少来源记录时，
首次会重新转换 DICOM，以免把已更换源影像的旧缓存发布为可复用结果。关闭功能时保留原缓存规则。

## 命中条件与产物

原始影像需同时满足体素值和物理几何一致。切片数量、尺寸等摘要只用于排除候选，
不能单独判定为同一序列。窗宽窗位、文件名和序列 UID 不参与影像等价判定。
具体使用解码后的体素、数据类型、尺寸、间距、原点和方向计算 SHA256；不比较
`nii.gz` 压缩文件的字节，也不对 HU 或几何做近似取整。当前 NIfTI 的指纹按文件代次保存，
后续输入未变时直接读取；查找只访问同图指纹目录中的索引，不逐个解压母目录内所有序列。

完整切割复用还要求部位、模型、算法版本和有效切割配置一致。改变层厚、层间距、
数量、范围、取景比例或 MPR/CPR 类型后，不能使用旧方案的 HU 切片结果。
仅修改窗宽窗位时可使用缓存中的未加窗 HU 数据，按当前请求重新加窗并输出。

复用写入本序列独立的版本快照，保留匹配信息、处理参数和所需数据。
A 处理完成后 B 命中 A，B 的完整快照不依赖 A 后续可变的输出路径；A 重新处理也不会
把 B 的旧方案更新成新方案。之后按不同方案重切 A 时，旧方案不会冒充新方案命中。

最终 DICOM、UID、源影像引用和报告必须根据当前请求生成，不能复制旧任务的成片和报告。
`cache/<模型>/segmentation/plans.json` 是 nnUNet 模型计划，不代表完整切割方案。

完整命中与仅分割命中的处理边界如下：

| 阶段 | 完整命中 | 只有同模型分割可复用 |
| --- | --- | --- |
| 1 DICOM / NIfTI | 仍校验本次来源，必要时转换并计算指纹 | 相同 |
| 2 nnUNet 分割 | 恢复快照，跳过推理 | 恢复快照，跳过推理 |
| 3 空间校正 | 恢复参数及工作影像，跳过计算 | 正常执行 |
| 4 标签定位 | 恢复结果，跳过计算 | 正常执行 |
| 5 解剖分析 | 恢复结果，跳过计算 | 正常执行 |
| 6 切割规划 | 恢复同方案的计划 | 按新方案重新规划 |
| 7 重建与输出 | 跳过 HU 采样、回正后取景及定位图几何计算，重新加窗写 DICOM | 正常执行 |
| 8 校验与报告 | 校验本次输出并生成本次报告 | 正常执行 |

模型缓存必须能确定当前 `nnUNet_results` 下的数据集、默认 trainer、实际生效的 plans、
configuration、fold、`checkpoint_final.pth`、`dataset.json` 和 `plans.json`。
这三个模型选项使用 `model_rules` 覆盖全局默认后的值；自定义 `plans` 也参与缓存身份校验。
模型文件、应用算法或有效配置变化时
旧版本不能冒充新版本。开启功能后，历史分割缺少这些来源凭据时首次可能重新推理；
关闭功能保留原来的本地缓存兼容规则。执行途中源数据或模型发生变化，不发布新的共享快照。
还会校验官方 nnUNet 启动入口、实际外部 Python 和 nnUNet 包源码，避免外部推理环境升级后
继续使用旧结果。该来源探测不导入 torch、不创建 CUDA 上下文；自定义包装命令无法确认来源时
保留原调用并禁用本次共享复用。

## 缓存目录与完成条件

每个序列仍使用自己的 `cache`，新增内容示意如下：

```text
<检查>/<序列>/cache/
  nifti/raw_0000.nii.gz
  metadata/source_provenance.json
  <模型>/segmentation/             # 原本地分割及侧车；B 复用后也有独立副本
    series_reuse.json              # 与当前影像及模型绑定的本地凭据
  series_reuse/
    volume.json                    # 本序列指纹和文件代次
    v1/<影像指纹>/<处理配置键>/<版本>/
      ready.json                   # 全部成功后发布，列出文件及校验和
      context.json                 # 校正、定位、解剖及实际切割计划
      segmentation/                # 与该快照绑定的分割、dataset/plans 等侧车
      files/                       # 实际用到的校正影像及其他处理产物
      hu/                          # 最终未加窗切片、逐片几何、取景和定位图
```

`hu` 使用无损且不含 pickle 的 NumPy 数组文件，保留采样后的数据类型；不保存
已经窗化截断的 DICOM 作为复用输入。校正工作影像原先可能位于部位输出目录的 `nifti/`，
现在所需文件会复制进持久化快照，成功任务清理中间目录后仍可复用。
`ready.json` 的 `summary` 另记录可直接查看的检查类型、切割部位、源图尺寸、
请求层厚/间距/数量/取景/切法、窗位和实际计划组数，排查时不需要根据配置哈希反推方案。

只有八阶段任务成功且输出校验通过，才原子发布整个版本目录。消费者先复制到自己的
私有目录并完整校验文件和 HU，再恢复结果；未完成、缺文件、校验失败的版本按未命中处理。
同一序列再次命中自己已完成的相同版本时复用已有版本，避免每次重切都再留一份相同快照。
任务中断的私有工作目录不参与查找；进程退出后，其遗留目录可在后续运行时清理。

例如 A/P1 完成、B/P1 复用后，A/P2 会重新规划和重建，可继续使用兼容的分割；
A 再切 P1 时仍可从 B 的 P1 版本读取。A 或 B 的输出目录重建不会覆盖另一序列的快照。

## 性能与使用范围

首次遇到的影像仍需要完整处理，并增加指纹和缓存写入成本。后续能跳过哪些步骤取决于
找到的缓存是否完整且配置兼容；大量不同序列不会因开启开关而自动省去推理。
目录初次建立索引、磁盘速度和缓存体积均影响耗时，具体提速以实际任务日志为准。
母目录应限于同一检查，避免扫描无关检查目录。

缓存会增加磁盘占用：每个接受复用的序列都有自己的分割、必要工作影像和 HU 副本，
不同有效方案保留各自版本。当前不自动淘汰已完成版本；检查级缓存清理应沿用服务端原有生命周期。
并发首次提交两个相同但都未完成的序列时，两者可能各自处理；本功能不新增跨序列排队等待。

测试已覆盖真实 DICOM 读写、同图不同窗、当前序列身份、A/B 独立、方案变化、缓存损坏、
模型变化和三 MPR/两 CPR 输出的像素及几何对照。测试替换了外部 nnUNet 推理，
不代表已测得生产病例的端到端加速比例。

如需恢复原逻辑，将 `series_reuse_enabled` 设为 `false`，无需删除已有缓存。
源码更新后需要按原发布流程重新构建和部署程序；修改源码不会自动替换已发布的可执行文件。
服务端调用代码与 Python 程序需配套更新：旧可执行文件不认识新增参数，先部署支持该参数的
Python 程序，再更新服务端调用。完整服务项目未包含在本仓库；服务端实际启动方法通过独立
C# 编译运行测试，整套服务仍需在其所属项目构建。
